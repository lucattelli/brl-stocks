# Build notes: slice 2

Notes for extracting a `build-increment` skill after this slice: where a decision was needed that no skill gave, what went into each PR, and what was awkward. Short entries, in order.

## 2026-11-24, night: setting up

- The user asked for the whole slice as a stack of PRs to review the next morning. Decisions that are the user's (the boundary change to the design, the emulator library of D86, spec questions) cannot wait for answers, so each PR builds on the recommended answer, marked "pending your approval", and the PRs above it are reworked if one is rejected. Spec questions are not recorded as decided; a test that needs one is skipped with its reason. A skill needs a rule for this: **work ahead on recommendations, never record them.**
- Stacked PRs: each branch starts from the one below and its PR targets it, so each PR shows only its own change. When the bottom one merges, the next is retargeted to `main`.
- The increments were planned in `scope.md` with D85's rules and checked by the same fresh agent as the scope. A first cut of four increments (29, 28, 27, 11) was regrouped after the scope check into five (35, 12, 15, 21, 11): the check saw that later increments needed the cache read, `--config` and the stand-in source from the first test on, and that one increment mixed two setups. Grouping by setup, not by story, is what the check enforces.
- The test boundary had to change before any test: the view's edge did not exist. `story-to-tests` stage 1 says a boundary change needs approval but not how to make one; done by hand plus one fresh critic, not with `design-alternatives` (too large for one edge).
- Implementation is done by a fresh builder agent per increment, which reads the spec, the design and the tests and must not edit the tests. No skill covers this yet; it keeps the coordinator's context for sorting findings.
- The boundary critic found eight real gaps in a first draft that looked complete: no way to know the view had settled (so "nothing changes" could not be tested without sleeping), unstated concurrency of the test driver, colour not deterministic under tests, key names that were the library's, no lifecycle for the input channel, the frame's shape. A boundary for an interactive surface needs a **settling signal** in its output; a skill should ask for it.
- Two critic findings were spec questions, not design (left/right arrows; header lines when scrolling). They go to the user as Q84, Q85 in PR 0; tests that need them are skipped.

## Increment 1

- Order on the branch: tests (red, own commit), build (own commit), verification (own commit), then push and open the PR. Pushing only once the build passes keeps CI from ever seeing a red commit, while the red commit still shows in history that the tests came first. A skill should say: **push after green, not after red.**
- The test writer found a boundary gap on its first run (Idle counted requests in flight, so "the fetch at start settled" could only be guessed with a quiet period). The fix was a design change on the increment's branch, not PR 0's, since PR 0 is pending anyway; the test writer was resumed to drop its workaround. A skill needs a rule for **boundary fixes found mid-stack**: fix in the lowest open PR, or in the current one with a note? Here: the current one, noted in the PR.
- The builder was a fresh agent with a brief (`increment-1/build-brief.md`): spec, design, code, tests; never edit tests; stop on any disagreement. It made six choices the spec or design left open and listed them; one was a spec gap (exit status when the terminal cannot be used: Q86). The coordinator's check: no test file changed, tests twice under `-race`, the other surface's verification still passes (the builder moved shared formatting).
- Working tree: the verifier and the next test writer cannot run at the same time in one working tree on different branches. Sequential here; a skill could use a worktree per agent.

## Increments 2 to 5

- Increments 2 and 3 had nothing to build: the view reused `print`'s rules and formatting (`render.Lines`, `market.Classify`), so their 27 tests passed at once. Green-at-once tests need proof they can fail; the writer did it on changed copies outside the repo, the coordinator by breaking one rule in the product and restoring it. A skill should require **one shown failure per green-at-once test** and say who does it. Scoping by setup put these increments where shared code already existed; an increment that needs no build is still worth its PR, because its verification is new.
- Running two agents at once in one working tree worked when their files did not overlap (a test writer on the next increment's test file while the verifier wrote under `verification/`), with each commit adding only its own files. It saved about a third of the wall time. A worktree per agent would remove the care needed.
- Every verifier finding that was not a fault was a spec gap at the edges of the screen (a long warning in the status line, the summary line at 40 columns, the exit status without a terminal). The acceptance tests did not see them because the test writer, rightly, asserted only what the criteria say. A skill could ask the verifier for **observations outside the criteria** as a standing part of its report; here they came unasked.
- PR descriptions followed one shape: evidence (tests, build, verification, one real screen), what was built on recommended answers, questions in the round shape, not verified with routes. CI passed on every PR at first push.
